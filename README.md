# Дипломный проект: тестирование приложения «Мобильный хоспис»

Дипломная работа по профессии «Инженер по тестированию» (Нетология).
Объект тестирования — Android-приложение **FMHAndroid** (`ru.iteco.fmhandroid`).

Работа состоит из двух этапов: ручное тестирование с подготовкой документации и автоматизация части проверок на Kotlin с использованием Espresso.

## Состав репозитория

### Первый этап — ручное тестирование

| Файл | Содержание |

### Почему автотесты выполняются на API 29

Выбор версии Espresso и уровня API обусловлен несовместимостями библиотеки:

- **Espresso 3.7.0**, поддерживающий Android 14 и выше, требует более новую версию Kotlin, чем используется в проекте.
- **Espresso 3.5.1** на Android 16 (API 36) падает с `NoSuchMethodException: InputManager.getInstance`.
- **Espresso 3.5.1** на API 28–30 при любом неуспешном сопоставлении элемента падает с `IncompatibleClassChangeError` вместо понятного сообщения об ошибке. Это подтверждённый дефект библиотеки: [android/android-test#1642](https://github.com/android/android-test/issues/1642). Ошибка возникает в коде формирования описания несовпадения и маскирует настоящую причину падения теста.

Рабочей оказалась комбинация **Espresso 3.4.0 + API 29**. Ручное тестирование при этом выполнено на API 36 согласно критериям оценки дипломной работы.

## Организация автотестов

Автотесты расположены в `app/src/androidTest/java/ru/iteco/fmhandroid/ui/` и разделены на пять классов по функциональности: `AuthTest` (4 теста — авторизация), `NewsTest` (4 теста — работа со списком новостей), `CreateNewsTest` (3 теста — создание новости), `NavigationTest` (5 тестов — навигация, экран About, раздел цитат) и `ZKnownIssuesTest` (1 тест, выявляющий дефект BUG-11, падение ожидаемо). Всего 17 тестов.

Тесты построены по шаблону **Page Object**. Работа с элементами интерфейса инкапсулирована в семи классах пакета `pages`: `AuthPage`, `MainPage`, `NewsPage`, `ControlPanelPage`, `CreateEditNewsPage`, `AboutPage`, `OurMissionPage`. Тестовые классы содержат только последовательность действий и проверок, обращений к Espresso напрямую в них нет.

Вспомогательный код собран в пакете `data`. `TestData` хранит учётные данные, названия категорий и генераторы уникальных заголовков. `Waiters` реализует ожидание появления элементов. `ScreenshotRule` делает снимок экрана при падении теста и прикладывает его к отчёту Allure.

Прогон выполняется инструментальным runner'ом `AllureAndroidJUnitRunner`, который формирует файлы результатов на устройстве.

Ожидания реализованы через `UiController.loopMainThreadForAtLeast()` — прокрутку очереди сообщений главного потока с ранним выходом по появлению элемента. Вызовы `Thread.sleep()` в проекте не используются.

Шаги для отчёта Allure оформлены вызовами `Allure.step("...") { ... }` вместо аннотации `@Step`: аннотация требует подключения AspectJ, несовместимого с версией Gradle в проекте.

## Подготовка к запуску

1. Клонировать репозиторий и открыть его в Android Studio. Файл `google-services.json` включён в репозиторий, дополнительная настройка не требуется.
2. Запустить эмулятор **Pixel 4, API 29**. Если эмулятор уже работал ранее, рекомендуется запуск через **Cold Boot** (Device Manager → ⋮ → Cold Boot Now).
3. Убедиться, что в эмуляторе есть доступ к сети: открыть браузер и загрузить любую страницу. Приложение проверяет сессию сетевым запросом и без соединения остаётся на экране загрузки.
4. Запустить приложение вручную и дождаться появления главного экрана или экрана авторизации. Если приложение не проходит экран загрузки, автотесты выполнить не удастся.

## Запуск автотестов

### Из Android Studio (основной способ)

Правый клик по пакету `app/src/androidTest/java/ru/iteco/fmhandroid/ui` → **Run 'Tests in ru.iteco.fmhandroid.ui'**.

Отдельный класс запускается правым кликом по файлу теста.

### Через Gradle

```
.\gradlew.bat connectedAndroidTest
```

Отчёт формируется в `app/build/reports/androidTests/connected/`.

Этот способ поднимает отдельный процесс сборки и требует значительно больше оперативной памяти. При открытой Android Studio на машинах с ограниченным объёмом памяти возможно зависание системы. Перед запуском рекомендуется закрыть Studio, а после прогона остановить фоновый процесс сборки:

```
.\gradlew.bat --stop
```

## Отчёт Allure

Результаты прогона формируются во внутреннем хранилище приложения на устройстве. Готовый архив последнего прогона уже находится в репозитории — `allure-results.zip`.

### Просмотр готового отчёта

Распаковать `allure-results.zip` в корень проекта и выполнить (требуется установленный [Allure CLI](https://allurereport.org/docs/install/)):

```
allure serve allure-results
```

### Выгрузка результатов нового прогона

```powershell
# Если adb отсутствует в PATH
Set-Alias adb "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"

# Скопировать результаты из внутреннего хранилища приложения
adb shell run-as ru.iteco.fmhandroid cp -r files/allure-results /sdcard/
adb pull /sdcard/allure-results
```

Перед новым прогоном результаты предыдущего необходимо удалить — иначе они попадут в отчёт вместе со свежими:

```powershell
Remove-Item -Recurse -Force allure-results -ErrorAction SilentlyContinue
adb shell run-as ru.iteco.fmhandroid rm -rf files/allure-results
adb shell rm -rf /sdcard/allure-results
```

## Результат прогона

| Показатель | Значение |
|---|---|
| Всего тестов | 17 |
| Пройдено | 16 |
| Падает | 1 |
| Время прогона | 2–3 минуты |

Тест `ZKnownIssuesTest.aboutScreenShouldBeOpenedFromNewsScreen` падает **ожидаемо**: он воспроизводит дефект BUG-11 — пункт меню About отключён на экране News (`is-enabled=false`), переход не выполняется. Тест останется красным до исправления дефекта.

В отчёте Allure этот тест помечен статусом **Broken**, а не Failed: экран About не открывается вообще, поэтому Espresso прерывает выполнение исключением `NoMatchingViewException` на этапе поиска элемента, не доходя до проверки.

Тестовый стенд использует общую базу данных, состав которой меняется между прогонами. Тесты создают собственные новости с уникальными заголовками вида `Autotest news <timestamp>`; созданные записи не удаляются. Подробнее об ограничениях автоматизации — в `Result.md`.
