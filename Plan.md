# План проверки и автоматизации приложения «Мобильный хоспис»

**Тестировщик:** Вероника
**Дата составления:** 01.08.2026

---

## 1. Объект тестирования

Мобильное приложение «Мобильный хоспис» для Android. Приложение предоставляет функциональность для работы с новостями хосписа и содержит раздел с тематическими цитатами.

**Структура приложения по результатам обследования:**

| Экран | Назначение | Способ перехода |
|---|---|---|
| Authorization | Вход в приложение | Стартовый экран |
| Main | Главный экран с сокращённым списком новостей | После входа, пункт меню Main |
| News | Полный список новостей, доступных пользователю | Пункт меню News, ссылка ALL NEWS |
| Filter | Фильтрация новостей по категории и датам | Иконка фильтра на экране News |
| Control panel | Управление новостями: создание, редактирование, удаление | Иконка панели на экране News |
| Creating News | Форма создания и редактирования новости | Кнопка создания в панели управления |
| Love is all | Тематические цитаты | Иконка в шапке приложения |
| About | Информация о приложении | Пункт меню About |

**Правило отображения новостей.** Новость отображается на экране News, если её статус ACTIVE и дата публикации не позже текущей. Новости со статусом NOT ACTIVE и новости с датой публикации в будущем доступны только в панели управления. Правило установлено опытным путём и требует подтверждения требованиями.

## 2. Границы тестирования

**Входит в область проверки:**

- пользовательский интерфейс всех экранов приложения;
- авторизация и управление сессией;
- просмотр, фильтрация и сортировка новостей;
- создание, редактирование и удаление новостей через панель управления;
- управление статусом публикации новости;
- раздел тематических цитат;
- обработка некорректного пользовательского ввода;
- поведение приложения при изменении состояния устройства и при недоступности сети.

**Не входит в область проверки:**

- серверная часть приложения — доступа к API и его документации нет, проверяется только реакция клиента на ответы;
- нагрузочное тестирование;
- тестирование на физических устройствах, проверка выполняется на эмуляторе;
- совместимость с версиями Android, отличными от указанной в критериях оценки;
- проверка вёрстки на различных размерах экрана.

Приложение собрано на устаревших версиях Gradle и AGP и рассчитано на более раннюю версию Android. Проверка выполняется на Android API 36 в соответствии с критериями оценки. Часть проверок предварительно выполнялась на Android 10 (API 29), расхождения в поведении зафиксированы отдельно.

## 4. Типы тестирования

- **функциональное тестирование** — основной объём проверок;
- **тестирование пользовательского интерфейса** — корректность отображения и реакции элементов;
- **негативное тестирование** — пустые, некорректные и граничные значения ввода;
- **тестирование граничных значений** — длинные строки, краевые пробелы, даты в прошлом и будущем;
- **тестирование удобства использования** — информативность сообщений и доступность разделов;
- **тестирование устойчивости** — поворот экрана, сворачивание, перезапуск приложения, отсутствие сети;
- **регрессионное тестирование** — реализуется через автоматизацию.

## 5. Подход к проверке

**Этап 1. Ручное тестирование.** Составлен чек-лист проверок (`Check.xlsx`) и тест-кейсы (`Cases.xlsx`). Проверки сгруппированы по функциональным блокам в соответствии со структурой приложения. Каждая проверка фиксируется со статусом и комментарием, выявленные дефекты оформляются баг-репортами. Фиксируется время прохождения чек-листа вручную для сравнительного отчёта на втором этапе.

**Этап 2. Автоматизация.** Тест-кейсы, отмеченные в `Cases.csv` как покрываемые, реализуются в виде UI-тестов на Espresso. Каждое действие завершается проверкой результата. Результаты прогона оформляются в отчёт Allure.

## 6. Подход к автоматизации

**Инструменты:** Espresso, JUnit 4, Allure.

**Организация тестов:**

- тесты размещаются в директории `androidTest`;
- группируются по функциональным блокам приложения в отдельные классы;
- используются понятные названия тестов, методов и элементов;
- повторяющиеся действия выносятся во вспомогательные методы;
- для каждого теста задаются предусловия, приводящие приложение в нужное состояние;
- каждое действие завершается проверкой.

**Особенность, влияющая на предусловия тестов.** Сессия пользователя сохраняется после перезапуска приложения. Тесты, требующие экрана авторизации, должны предварительно выполнять выход из аккаунта.

**Разметка для отчёта Allure:** названия функциональностей, описания тестов, шаги, прикрепление снимков экрана при падении.

**Что не покрывается автотестами и почему:**

| Категория проверок | Причина |
|---|---|
| Сворачивание приложения и возврат из списка задач | Espresso работает только внутри процесса приложения |
| Полный перезапуск приложения | Завершение процесса прерывает выполнение теста |
| Поведение при отсутствии сети | Требуется изменение состояния сети на устройстве |
| Проверки по содержимому сетевых запросов | Проверка выполняется по логу, а не по интерфейсу |
| Установка и запуск приложения на целевой версии API | Проверка выполняется вне интерфейса приложения |

Отметки о покрытии проставлены индивидуально для каждого тест-кейса в файле `Cases.xlsx`.

## 7. Техники тест-дизайна

| Техника | Где применяется | Обоснование |
|---|---|---|
| Эквивалентное разделение | Поля ввода логина и пароля, поля формы создания новости, выбор категории | Позволяет сократить число проверок, разделив значения на классы: корректные, пустые, некорректные по формату. Проверка одного представителя класса даёт тот же результат, что и проверка всех значений класса |
| Анализ граничных значений | Длина полей ввода, даты публикации относительно текущей даты, краевые пробелы в логине и пароле | Дефекты чаще проявляются на границах диапазонов. Для приложения критична граница «дата публикации сегодня / в будущем», определяющая видимость новости пользователям |
| Тестирование состояний и переходов | Статусы новости ACTIVE и NOT ACTIVE, состояние сессии пользователя, развёрнутое и свёрнутое состояние карточек | Новость имеет конечный набор состояний и правил перехода между ними. Техника позволяет проверить каждый переход и убедиться, что состояние корректно отражается на всех экранах |
| Попарное тестирование | Сочетание статуса новости и даты публикации при определении видимости на экране News | Видимость новости определяется двумя параметрами одновременно. Проверка всех сочетаний даёт полное покрытие правила отображения при небольшом числе тестов |
| Тестирование на основе сценариев использования | Полные пользовательские сценарии: вход, создание новости, редактирование, удаление, выход | Проверяет работоспособность приложения на реальных последовательностях действий, а не только на изолированных функциях |
| Исследовательское тестирование | Все экраны приложения, поведение при отсутствии сети, при повороте экрана и сворачивании | Документация с требованиями к приложению отсутствует. Исследовательское тестирование позволяет выявить неочевидное поведение и уточнить фактические правила работы приложения, которые затем фиксируются в чек-листе |

## 8. Интервальная оценка трудозатрат с учётом рисков

Оценка приведена интервалом: нижняя граница соответствует работе без осложнений, верхняя учитывает риски, перечисленные в разделе 9.

| Этап работ | Оптимистичная оценка | Пессимистичная оценка |
|---|---|---|
| Настройка окружения: эмулятор целевой версии API, сборка и запуск приложения | 1 ч | 2 ч |
| Обследование приложения, составление плана, чек-листа и тест-кейсов | 5 ч | 7 ч |
| Ручное прохождение чек-листа с фиксацией результатов, включая перепроверку выявленных дефектов | 4 ч | 6 ч |
| Оформление баг-репортов | 1 ч | 2 ч |
| Настройка проекта для UI-тестов, подключение Espresso и Allure | 2 ч | 4 ч |
| Написание автотестов | 8 ч | 14 ч |
| Отладка автотестов, устранение нестабильности | 3 ч | 8 ч |
| Формирование отчёта Allure и выгрузка результатов с устройства | 1 ч | 3 ч |
| Подготовка итоговой отчётности | 1 ч | 2 ч |
| **Итого** | **26 ч** | **48 ч** |

Разброс по ручному прохождению чек-листа обусловлен необходимостью перепроверки выявленных дефектов: часть наблюдений при повторной проверке не подтвердилась и была снята, что потребовало дополнительных прогонов. Основной разброс по проекту в целом приходится на написание и отладку автотестов. Он обусловлен тремя факторами: приложение собрано на устаревших версиях Gradle и AGP, что может потребовать подбора совместимых версий тестовых библиотек; часть элементов интерфейса не имеет идентификаторов, пригодных для поиска; тестовые данные хранятся на общем сервере и изменяются между прогонами, что требует создания собственных данных в предусловиях каждого теста.

| Выгрузка отчёта Allure с устройства на актуальных версиях Android требует дополнительной настройки доступа к файлам | Задержка на этапе формирования отчёта | Настройка выполняется до написания основного объёма тестов |

## 11. Вопросы к требованиям и принятые решения

Документация с требованиями к приложению отсутствует. Перечисленные ниже особенности поведения выявлены в ходе исследовательского тестирования. По каждой принято решение о том, считать ли поведение ожидаемым, на основании логики работы приложения и общепринятой практики.

| № | Особенность поведения | Принятое решение |
|---|---|---|
| 1 | Логин и пароль регистрозависимы | Ожидаемое поведение, соответствует общепринятой практике обработки учётных данных |
| 2 | Краевые пробелы обрезаются в логине и в пароле | Ожидаемое поведение для логина. Для пароля обрезка спорна, поскольку пробел может быть значимым символом, однако риск невелик и дефектом не считается |
| 3 | Ограничение длины полей ввода отсутствует | Приложение остаётся стабильным при вводе строк длиной более 200 символов, данные сохраняются и корректно отображаются. Дефектом не считается |
| 4 | При неверных учётных данных отображается общее сообщение о технической ошибке | Считается дефектом, оформлен как BUG-01: сообщение не позволяет пользователю понять причину отказа |
| 5 | Сортировка выполняется по дате публикации и сбрасывается при возврате на экран | Ожидаемое поведение, сохранение состояния сортировки между переходами не является обязательным |
| 6 | Сессия сохраняется после полного перезапуска приложения | Ожидаемое поведение, соответствует практике мобильных приложений. Учтено в предусловиях тест-кейсов и автотестов |
| 7 | Главный экран отображает сокращённый список новостей | Ожидаемое поведение, полный список доступен на экране News по ссылке ALL NEWS |
| 8 | Новость с датой публикации в будущем не отображается на экране News | Ожидаемое поведение, соответствует механизму отложенной публикации. Новость остаётся доступной в панели управления |
| 9 | Разрешение на отправку уведомлений не запрашивается | Функционал уведомлений в приложении не обнаружен, запрос разрешения не требуется. Дефектом не считается |
| 10 | Раздел цитат доступен только по неподписанной иконке в шапке | Считается дефектом удобства использования, оформлен как BUG-06: назначение иконки неочевидно, раздел может остаться незамеченным |
