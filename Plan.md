# План проверки и автоматизации приложения «Мобильный хоспис»

**Тестировщик:** Вероника
**Дата составления:** 01.08.2026

---

## 1. Объект тестирования

Мобильное приложение «Мобильный хоспис» для Android. Приложение предоставляет функциональность для работы с новостями хосписа и содержит раздел с тематическими цитатами.

**Структура приложения по результатам обследования:**

| Экран | Назначение | Способ перехода |
|---|---|---|
| Authorization | Вход в приложение | Стартовый экран |
| Main | Главный экран с сокращённым списком новостей | После входа, пункт меню Main |
| News | Полный список новостей, доступных пользователю | Пункт меню News, ссылка ALL NEWS |
| Filter | Фильтрация новостей по категории и датам | Иконка фильтра на экране News |
| Control panel | Управление новостями: создание, редактирование, удаление | Иконка панели на экране News |
| Creating News | Форма создания и редактирования новости | Кнопка создания в панели управления |
| Love is all | Тематические цитаты | Иконка в шапке приложения |
| About | Информация о приложении | Пункт меню About |

**Правило отображения новостей.** Новость отображается на экране News, если её статус ACTIVE и дата публикации не позже текущей. Новости со статусом NOT ACTIVE и новости с датой публикации в будущем доступны только в панели управления. Правило установлено опытным путём и требует подтверждения требованиями.

## 2. Границы тестирования

**Входит в область проверки:**

- пользовательский интерфейс всех экранов приложения;
- авторизация и управление сессией;
- просмотр, фильтрация и сортировка новостей;
- создание, редактирование и удаление новостей через панель управления;
- управление статусом публикации новости;
- раздел тематических цитат;
- обработка некорректного пользовательского ввода;
- поведение приложения при изменении состояния устройства и при недоступности сети.

**Не входит в область проверки:**

- серверная часть приложения — доступа к API и его документации нет, проверяется только реакция клиента на ответы;
- нагрузочное тестирование;
- тестирование на физических устройствах, проверка выполняется на эмуляторе;
- совместимость с версиями Android, отличными от указанной в критериях оценки;
- проверка вёрстки на различных размерах экрана.

Приложение собрано на устаревших версиях Gradle и AGP и рассчитано на более раннюю версию Android. Проверка выполняется на Android API 36 в соответствии с критериями оценки. Часть проверок предварительно выполнялась на Android 10 (API 29), расхождения в поведении зафиксированы отдельно.

## 4. Типы тестирования

- **функциональное тестирование** — основной объём проверок;
- **тестирование пользовательского интерфейса** — корректность отображения и реакции элементов;
- **негативное тестирование** — пустые, некорректные и граничные значения ввода;
- **тестирование граничных значений** — длинные строки, краевые пробелы, даты в прошлом и будущем;
- **тестирование удобства использования** — информативность сообщений и доступность разделов;
- **тестирование устойчивости** — поворот экрана, сворачивание, перезапуск приложения, отсутствие сети;
- **регрессионное тестирование** — реализуется через автоматизацию.

## 5. Подход к проверке

**Этап 1. Ручное тестирование.** Составлен чек-лист проверок (`Check.xlsx`) и тест-кейсы (`Cases.xlsx`). Проверки сгруппированы по функциональным блокам в соответствии со структурой приложения. Каждая проверка фиксируется со статусом и комментарием, выявленные дефекты оформляются баг-репортами. Фиксируется время прохождения чек-листа вручную для сравнительного отчёта на втором этапе.

**Этап 2. Автоматизация.** Тест-кейсы, отмеченные в `Cases.csv` как покрываемые, реализуются в виде UI-тестов на Espresso. Каждое действие завершается проверкой результата. Результаты прогона оформляются в отчёт Allure.

## 6. Подход к автоматизации

**Инструменты:** Espresso, JUnit 4, Allure.

**Организация тестов:**

- тесты размещаются в директории `androidTest`;
- группируются по функциональным блокам приложения в отдельные классы;
- используются понятные названия тестов, методов и элементов;
- повторяющиеся действия выносятся во вспомогательные методы;
- для каждого теста задаются предусловия, приводящие приложение в нужное состояние;
- каждое действие завершается проверкой.

**Особенность, влияющая на предусловия тестов.** Сессия пользователя сохраняется после перезапуска приложения. Тесты, требующие экрана авторизации, должны предварительно выполнять выход из аккаунта.

**Разметка для отчёта Allure:** названия функциональностей, описания тестов, шаги, прикрепление снимков экрана при падении.

**Что не покрывается автотестами и почему:**

| Категория проверок | Причина |
|---|---|
| Сворачивание приложения и возврат из списка задач | Espresso работает только внутри процесса приложения |
| Полный перезапуск приложения | Завершение процесса прерывает выполнение теста |
| Поведение при отсутствии сети | Требуется изменение состояния сети на устройстве |
| Проверки по содержимому сетевых запросов | Проверка выполняется по логу, а не по интерфейсу |
| Установка и запуск приложения на целевой версии API | Проверка выполняется вне интерфейса приложения |

Отметки о покрытии проставлены индивидуально для каждого тест-кейса в файле `Cases.xlsx`.

## 7. Выявленные дефекты

| ID | Описание | Приоритет | Экран |
|---|---|---|---|
| BUG-01 | При любом некорректном вводе учётных данных отображается общее сообщение о технической ошибке вместо сообщения об ошибке авторизации | Low | Authorization |
| BUG-03 | Кнопка REFRESH в пустом состоянии экрана News не выполняет никакого действия, единственный выход из состояния — системная кнопка «Назад», возвращающая на главный экран | Medium | News |
| BUG-04 | При вводе произвольного текста в поле категории фильтра запрос не выполняется и пользователь не получает обратной связи | Medium | Filter |
| BUG-05 | Введённые данные теряются при повороте экрана авторизации, обратный поворот их не восстанавливает | Medium | Authorization |
| BUG-06 | Дата создания новости отображается некорректно: год выводится пятизначным числом в диапазоне 58xxx | Medium | Control panel |
| BUG-07 | Раздел цитат недоступен из меню навигации и вызывается только неподписанной иконкой в шапке | Low | Навигация |
| BUG-08 | Поле Category допускает ввод произвольного текста, при сохранении отображается сообщение о технической ошибке вместо указания на некорректную категорию | Medium | Creating News |
| BUG-09 | Индикаторы незаполненных полей не сбрасываются после заполнения формы и остаются на корректно заполненных полях | Low | Creating News |
| BUG-10 | Переключатель Active недоступен для взаимодействия на форме создания новости, при редактировании работает корректно | Medium | Creating News |
| BUG-11 | Ссылки Privacy Policy и Terms of use на экране About не открываются, домен не резолвится | Low | About |
| BUG-12 | Пункт меню About недоступен на экране News, при этом доступен с экрана Main, из панели управления и с экрана цитат | Medium | Навигация |
| BUG-13 | В диалоге подтверждения отмены создания новости отображается текст о выходе из аккаунта вместо отмены изменений | Low | Creating News |

**Наблюдения, не являющиеся дефектами:**

- краевые пробелы обрезаются и в логине, и в пароле, логин и пароль регистрозависимы;
- ограничение длины полей ввода не обнаружено ни в авторизации, ни в форме создания новости;
- сессия сохраняется после полного перезапуска приложения, повторная авторизация не требуется;
- главный экран отображает сокращённый список новостей, полный список доступен на экране News;
- фильтрация новостей выполняется на стороне клиента по ранее загруженным данным, сетевой запрос при применении фильтра не отправляется, на результат для пользователя это не влияет;
- сортировка сбрасывается к исходной при возврате на экран;
- выбор даты публикации в прошлом заблокирован в календаре;
- формы фильтрации на экране News и в панели управления различаются: в панели дополнительно доступны чекбоксы Active и Not active;
- приложение системно не различает типы ошибок в сообщениях пользователю: одинаковый текст отображается при неверных учётных данных, при некорректной категории и при отсутствии сети;
- в тексте диалога удаления новость называется документом;
- при первом запуске приложение не запрашивает разрешение на отправку уведомлений;
- в приложении присутствуют новости с тестовыми данными других пользователей, состав списка меняется между прогонами.

**Расхождение поведения между версиями Android.** На Android 10 ориентация экрана не менялась и потеря данных при повороте не воспроизводилась. На Android 16 поворот выполняется, дефект BUG-05 проявляется. Проверка на целевой версии API является обязательной.

## 8. Риски

| Риск | Влияние | Меры |
|---|---|---|
| Приложение собрано на устаревших версиях Gradle и AGP, поведение на Android API 36 может отличаться от заложенного разработчиком | Часть проверок может давать результаты, не предусмотренные разработчиком | Проверки выполняются на целевой версии API, расхождения фиксируются отдельно |
| Отсутствие документации с требованиями | Часть ожидаемых результатов определяется по общепринятой практике | Спорные случаи вынесены в список вопросов |
| Дефект BUG-02 блокирует проверку фильтрации по существу | Сценарии фильтрации непроверяемы до исправления | Проверки зафиксированы как непройденные, автотесты пишутся на ожидаемое поведение |
| Тестовые данные в приложении создаются разными пользователями и могут изменяться между прогонами | Возможны нестабильные результаты проверок, зависящих от состава списка | Тесты создают собственные данные в предусловиях и не полагаются на существующие новости |
| Выгрузка отчёта Allure с устройства на актуальных версиях Android требует дополнительной настройки доступа к файлам | Задержка на этапе формирования отчёта | Настройка выполняется до написания основного объёма тестов |

## 9. Вопросы к требованиям

1. Является ли регистрозависимость логина ожидаемым поведением?
2. Должны ли краевые пробелы в пароле обрезаться, если пробел может быть значимой частью пароля?
3. Предусмотрено ли ограничение длины полей ввода и какое именно?
4. Какое сообщение должно отображаться при вводе неверных учётных данных?
5. По какому полю выполняется сортировка новостей и предусмотрен ли выбор направления?
6. Является ли сохранение сессии после перезапуска приложения ожидаемым поведением?
7. Сколько новостей должно отображаться в сокращённом списке на главном экране и по какому правилу они отбираются?
8. Должна ли новость с датой публикации в будущем скрываться от пользователей до наступления этой даты?
9. Предусмотрен ли запрос разрешения на отправку уведомлений и реализован ли функционал уведомлений?
10. Должен ли раздел цитат быть доступен из меню навигации?
